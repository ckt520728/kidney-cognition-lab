我同時用了 5 個 AI 寫程式助手——真實實戰比較

三個月、五個工具、一百多個坑：Codex、Claude Code、OpenCode、Antigravity、Hermes Agent 的田野調查報告

AI Coding Agent Codex Claude Code OpenCode Antigravity Hermes Agent 實戰比較

從 2026 年 4 月到 6 月，我花了將近三個月，同時用五個 AI 寫程式助手：OpenAI 的 Codex、Anthropic 的 Claude Code、開源的 OpenCode（搭 GLM-5.2）、Google 的 Antigravity、還有 Nous Research 的 Hermes Agent。這不是開箱文，是踩了近百個坑之後的真實心得。

為什麼要同時用五個？

因為沒有一個能搞定所有事。

我是一個腎臟科醫師，同時做計算神經科學研究。我的日常工作很雜：早上讀 PubMed 新文獻、下午寫論文審稿、晚上做互動式教學網站、偶爾還要搞一個 Telegram bot 每天自動推播 AI 新聞到手機。

每個 AI 助手都有它擅長的場景。與其找一個「全能」的，不如搞清楚哪個場合用哪個。這篇文章就是這三個月來的田野調查報告。

一、操作技巧：誰擅長什麼？

Skill 打包與分享：Codex > Claude Code > OpenCode

三個工具都有 Skill 系統——把工作流封裝成可重複使用的技能包——但打包流程差很多。

Codex 的 Skill 打包最成熟，但上傳 claude.ai 時有四個陷阱：zip 結構、路徑分隔符、根目錄名、frontmatter name: 欄位。最狡猾的是第 3 和第 4 個錯誤訊息一字不差但根因完全不同——一個指 zip 內的資料夾名，一個指 SKILL.md 裡的 name: 欄位。我連續失敗 4 次才搞懂。

踩坑教訓：錯誤訊息一樣不代表根因一樣 Codex Skill 上傳第 3 次和第 4 次的錯誤訊息文字完全相同：root directory name must contain only alphanumeric characters, underscores, and hyphens。但第 3 次的根因是 zip 內根目錄名含中文，第 4 次的根因是 SKILL.md frontmatter 的 name: 欄位含中文。不知道這點會陷入無限迴圈。

另外，PowerShell 的 Compress-Archive 不能用——它把路徑分隔符寫成 \，但 ZIP 標準必須用 /。得用 .NET 的 System.IO.Compression.ZipArchive 手動處理。

Claude Code 的 Skill 生態也很完整，而且可以上傳到 claude.ai 分享。它的 SKILL.md 有標準結構（frontmatter → 鐵則 → 工作流程 → 編輯原則），共同原則是「零外部 LLM API 依賴、零捏造、反 LLM 陳腐用詞」。

MCP 連接能力：OpenCode >> Codex > Claude Code ≈ Hermes

MCP（Model Context Protocol）是讓 AI 助手連接外部服務的協議。連得越多，能做的事越多。

OpenCode 是 MCP 整合之王。我的設定檔裡同時連了 NotebookLM（151 個筆記本的語意檢索）、Firebase（資料庫）、Obsidian（知識庫 vault）、Gmail（一度想接但 OAuth 踩坑連連）。設定完重啟一次就全部生效。

Codex 的 MCP 連接也不錯，但設定檔是 TOML 格式，Windows 路徑要寫雙反斜線 C:\\Users\\...，修改後必須完整重啟 Codex Desktop。

Hermes Agent 不走 MCP 路線，它用自己的 plugin 系統。但它的 Telegram bot 整合是獨門絕活——你可以在手機上用 Telegram 跟它講話，它就幫你建 CRON 排程、改模型設定、跑任務。

人機協作模式：Antigravity > Claude Code > Codex

Antigravity 的「雙環迭代機制」是我用過最友善的協作模式。它不直接改你的稿子，而是先生一份 implementation_plan.md（預計修改條目、科學論據、擬新增文獻），讓你先看再批准。你可以在計畫裡加 comment 微調，它收到微調後重新精確計算並更新計畫，直到你說 Proceed 才動手。

Antigravity 雙環迭代的價值 第一環「無損回饋」——不直接改稿而是先生計畫供使用者微調，避免一改就錯。第二環 walkthrough 報告讓使用者一眼掌握微調後的最終呈現。對學術論文審查簡直是完美——不怕一改就錯。

Claude Code 的多代理人管線有類似的精神（Grounding Gate → BTL Tournament → Self-Healing Synthesis），但更自動化、更適合大量文獻的批量分析。

定時自動化：Hermes Agent >> Codex > OpenCode

Hermes Agent 的 CRON + Telegram 推播組合是全場最實用的自動化方案。我設了一個每天早上 8 點的 CRON，自動抓 PubMed（腎臟學 + 認知神經）+ arXiv（AI 論文）+ 五家 AI 新聞 RSS，用 GPT-5.5 整理成四區塊推到手機。完全免費、不綁信用卡、雲端排程不靠電腦開著。

但 Hermes 有個「自反性死結」陷阱：

Hermes 最獨家的坑：自反性死結 quota 用完時，你想用 Telegram 叫 bot 改模型，但 bot 的對話本身也用 Main Model——Main Model 壞了 bot 連解析「請改模型」都做不到。這時只能繞過 Telegram，直接用 PowerShell CLI 救。這是「對話為主」原則的唯一例外：對話通道故障時，CLI 才是唯一救星。

圖像生成：Codex 獨佔

只有 Codex 內建 gpt-image-2（OpenAI 的圖像生成模型）。Codex 訂閱者免設 API key 就能生圖。我的 SOIL 教學簡報工作流就是靠這個：OpenCode（GLM-5.2）跑引擎 1-5 產 prompt → 到 Codex Desktop 生圖 → 圖回來後 OpenCode 做 QA + 打包。其他四個工具都沒有內建圖像生成。

二、碰到的坑：共同陷阱 vs 獨家地雷

五個工具都會踩的共同陷阱

PowerShell 5.1 是 Windows 上 AI agent 的最大敵人

這五個工具在 Windows 上都踩過同一批 PowerShell 坑：

  • Set-Content / Out-File 預設寫 UTF-16 LE with BOM，破壞中文 → 全部改用 .NET UTF8Encoding($false) 寫無 BOM UTF-8。
  • 含中文路徑 Test-Path / Join-Path 失敗 → 先 cp 到 ASCII 路徑再用 -LiteralPath。
  • ConvertFrom-Json 在 PS 5.1 是 case-insensitive，JSON 有 .c 跟 .C 兩個 key 時會誤判。
  • PowerShell 管線傳中文 JSON 變 ?? → 先用 ASCII 路徑測試確認管線正常。

Anaconda DLL load failed 是同一個根因

conda Library\bin 沒掛 PATH，只有 conda activate 才會掛。PIL 和 numpy 都會中招。治本解法是 import enable_conda_dlls，不要重灌 Anaconda。這個坑我在 OpenCode 和 Claude Code 上都踩過，花了兩天才搞清楚是同一個原因。

三、實務經驗：每個 AI 的獨門絕活

Codex：自動化心跳與圖像生成的王者

Codex 最獨特的能力是 heartbeat automation——排程每天自動執行任務。我用它做 OpenClaw + LINE 生活助理的自動恢復：每天早上 7:05 自動檢查 LINE webhook 是否活著，tunnel 停了就重建並更新 endpoint。這是其他四個工具都做不到的。

另外，gpt-image-2 內建是巨大優勢。我的 SOIL 教學簡報工作流（六顆引擎的教學設計 → AI 逐頁生圖 → 打包 PPTX）完全依賴 Codex 的圖像生成能力。其他工具要生圖只能走跨工具協作模式。

Claude Code：多代理人學術分析的泰斗

Claude Code 的 Robin MAS（Multi-Agent System）是我用過最成熟的多代理人研究管線。15 個 agent、971 秒、52 萬 tokens，產出一份 Reject 3.5/10 的論文評審報告——三條獨立數學軌跡都抵達同一個結論，Grounding Gate 還抓到了作者摘要裡的錯誤數字。

Grounding Gate 的價值 論文摘要寫 EigenWorms 83.9%，但 Grounding Agent 讀完全文發現這是 S5 baseline 的數字，PHCSSM 本身其實是 85.0%。更重要的是，GPU 記憶體「10-48MB」論文裡根本沒寫——是模型從摘要推測編造的。Grounding Gate 把這些全部標為 hallucination_flags。

最讓我印象深刻的是 BTL Tournament（Bradley-Terry-Luce 錦標賽排名）：當兩個 agent 對同一個論點有矛盾時，不是讓一個 Monitor 裁判，而是讓它們兩兩比對「誰有更直接的論文佐證」。這比直接打分數穩得多，位置偏差也更少。

OpenCode：MCP 整合與跨工具協作的樞紐

OpenCode 的最大價值是「樞紐」——它能同時連接 NotebookLM（語意檢索 151 個筆記本）、Obsidian（結構化知識庫）、Firebase（資料庫），然後用 GLM-5.2 當大腦做跨來源整合。

我用它做了 Sussillo vs Richards 研究方法論八維度對比表：同時查兩個 NotebookLM 筆記本（45 sources + 23 sources），由 LLM 做 cross-referencing，效率遠優於逐一查詢。最後產出的結論是：

Sussillo 說大腦是動力學幾何；Richards 說大腦是資料生成引擎。兩者都是對的。

它也是跨工具協作的中心：OpenCode 產 prompt → Codex 生圖 → OpenCode 做 QA + 打包。沒有 OpenCode 的 MCP 整合能力，這個工作流跑不起來。

Antigravity：最懂「人類想審查」的夥伴

Antigravity 的雙環迭代（Implementation Plan ⇄ Walkthrough）是我用過最舒服的人機協作節奏。它做學術論文審查時，不直接改稿，而是先給你一份計畫：「我打算改這 7 個地方，引用這 5 篇文獻，架構這樣調整。」你可以加 comment 微調，它收到後重新精確計算，直到你批准才動手。

而且它的 sync_index.py 把 React app 打包成單一靜態 HTML 的模式非常優雅——去 imports、去 export default、注入 template placeholder、寫出 UTF-8。改完 code 跑一行指令就同步，雙擊 HTML 就能跑，不用裝任何依賴。這對要帶去演講現場 demo 的人來說是救命功能。

Hermes Agent：手機就能控制的 AI 管家

Hermes 最獨特的是 Telegram bot 整合。我可以在通勤時用手機跟 bot 講話：「幫我建一個 CRON，每天早上 8 點抓 PubMed 腎臟學新文獻，傳送至 origin。」bot 自己呼叫 cronjob create 就建好了。Dashboard 點按鈕做不到的事（比如 origin delivery mode），用講的反而一句話搞定。

它的 Multi-Agent Kanban + 資料合約也很有意思：researcher 寫 literature_map.md → coder 讀它寫 validation_plan.md → reviewer 讀兩份寫 review.md。每份 SOUL.md 有「給下一棒的交棒清單」——coder 不用通讀 literature_map 也能定位重點，reviewer 不用憑空判斷 coder 哪裡心虛。這比單純的「角色描述」高了一個檔次。

不過 Hermes 最大的代價是 Windows 水土不服——我踩了 24 個坑才跑通。從 gateway start 卡死（要用 gateway run）到 ui 不存在（要用 dashboard），從 sudo 提示無意義到 UAC 迴圈，全是 Linux 慣例在 Windows 上的翻譯問題。

如果只能選一個

  • 如果你是研究者，選 Claude Code——Robin MAS 的深度分析能力無可替代。
  • 如果你是教學者，選 Antigravity——雙環迭代 + 靜態部署最適合做教學工具。
  • 如果你是臨床醫師想自動化日常，選 Hermes Agent——每天早上手機收到文獻 brief 的體驗太好了。
  • 如果你是開發者想最大彈性，選 OpenCode——開源、模型可替換、MCP 整合最強。
  • 如果你需要圖像生成，選 Codex——gpt-image-2 內建是獨家。

但最好的答案其實是：組合使用。 我的日常工作流就是 OpenCode 當樞紐（MCP 整合）+ Claude Code 做深度分析（Robin MAS）+ Codex 生圖 + Hermes Agent 每天推播 + Antigravity 做需要審查的修改。五個工具各司其職，加起來大於任何單一個。

Take-home Messages

  1. 沒有全能工具，只有適合場景。五個工具各有所長，組合使用的效果遠大於單選一個。
  2. 錯誤訊息一樣不代表根因一樣。Codex Skill 上傳的第 3 和第 4 次錯誤訊息一字不差，但根因完全不同。除錯時要先看 stack trace，不要靠錯誤訊息文字猜。
  3. PowerShell 5.1 是 Windows 上所有 AI agent 的共同敵人。編碼（UTF-16 BOM）、中文路徑、case-insensitive JSON 是三大重複踩坑點。治本解法一律是 .NET UTF8Encoding($false) + -LiteralPath。
  4. 「對話為主」原則有例外。Hermes 的「跟 bot 講話最有效」在 quota 用完時失效——bot 自己也壞了。對話通道故障時，CLI 才是唯一救星。
  5. 免費方案有陷阱。Hermes 的 40+ provider 只有 2 個真免費；PubMed 無 key 每秒 3 欲求有 key 才到 10 次。訂閱官方郵件追蹤免費 promo 輪換是必要的。
  6. 一百多個坑，換來的是一套知道什麼時候用什麼工具的直覺。希望這篇文章能幫你少踩幾個。
